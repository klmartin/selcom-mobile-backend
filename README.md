# Selcom mobile payment backend

A small Node.js/Express API for one merchant to collect Tanzanian mobile-money payments. It uses MySQL, the official Selcom client's request signing, persistent idempotency, signed callbacks, and status reconciliation. The application sends real provider requests once configured. Automated tests use a fake provider.

## 1. Install

Requirements: Node.js **22 or newer**, npm, and an accessible **MySQL 8+** database. The SQL integration tests were also exercised on MariaDB; see `TESTING.md` for exact results. Use a separate database for this application.

Extract the ZIP and enter its directory. On Ubuntu/Linux:

```sh
unzip selcom-mobile-backend.zip
cd selcom-mobile-backend
sh install.sh
nano .env
```

On Windows PowerShell:

```powershell
Expand-Archive .\selcom-mobile-backend.zip -DestinationPath .\selcom-project
cd .\selcom-project\selcom-mobile-backend
npm ci
npm run setup
notepad .env
```

The installer installs dependencies and creates `.env` with a random `APP_API_KEY`. It preserves an existing `.env`. It does not contact Selcom, create charges, install MySQL, or deploy a public website.

## 2. Create the database

Connect using your local MySQL administrator (`sudo mysql` on many Ubuntu installations). Replace the password below with your own, then enter this SQL:

```sql
CREATE DATABASE selcom_payments CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
CREATE USER 'selcom_app'@'127.0.0.1' IDENTIFIED BY 'REPLACE_WITH_A_STRONG_DATABASE_PASSWORD';
GRANT SELECT, INSERT, UPDATE, DELETE, CREATE, ALTER, INDEX, REFERENCES
ON selcom_payments.* TO 'selcom_app'@'127.0.0.1';
```

For a remote database, ask its administrator to create the equivalent user restricted to your backend's source address. Use a verified TLS CA with `DB_SSL_CA_FILE` when needed. The app never creates or drops databases automatically.

## 3. Fill in `.env`

| Setting | Value to supply |
| --- | --- |
| `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, `DB_PASSWORD` | Your dedicated database connection |
| `SELCOM_BASE_URL` | The HTTPS API base URL provided for your Selcom account; omit `/v1/checkout` |
| `SELCOM_API_KEY`, `SELCOM_API_SECRET` | Your Selcom credentials |
| `SELCOM_VENDOR` | Your assigned merchant/vendor identifier |
| `PUBLIC_WEBHOOK_URL` | Your public HTTPS URL ending in `/api/v1/webhooks/selcom` |
| `APP_API_KEY` | Already generated by setup; use it only from trusted backend clients |

Leave the three-minute reconciliation intervals at their defaults unless Selcom directs otherwise. The installer does not select UAT versus production: **the account credentials and actual base URL determine the environment**. Obtain those values from Selcom. No live API host or credentials are hardcoded.

The callback URL in `.env` is a normal HTTPS URL; the service encodes it for the outgoing Selcom order. Do not pre-encode it yourself.

## 4. Create tables and start

```sh
npm run migrate
npm start
```

In another terminal:

```sh
curl http://127.0.0.1:3080/health
```

Expected: `{"status":"ok"}`. Configuration is validated before listening. `HOST=127.0.0.1` keeps the app behind your reverse proxy. The status worker runs in the app by default, so no cron job is necessary.

For your existing PM2 installation:

```sh
pm2 start ecosystem.config.cjs
pm2 save
pm2 logs selcom-payments --lines 30
```

Use a dedicated non-root operating-system user for the process. The provided PM2 configuration starts one instance and gives in-flight requests time to finish on shutdown.

## 5. Publish HTTPS and the callback

Attach your domain to this backend's public address and configure a valid HTTPS certificate. `deploy/nginx.conf.example` shows an Nginx reverse proxy to port 3080; adapt it to your existing server. Replace the hostname and certificate paths before enabling it. If Nginx already handles HTTPS for your domain, add the proxy configuration to that existing server block.

Set `TRUST_PROXY_HOPS=1` **only** when exactly one trusted reverse proxy is in front of the app and the application port cannot be reached directly by untrusted clients. The Nginx example overwrites forwarded client headers. Leave it at `0` for direct local access.

Give Selcom this URL, replacing the hostname:

```text
https://YOUR-DOMAIN/api/v1/webhooks/selcom
```

Use the same URL in `PUBLIC_WEBHOOK_URL`. Ensure Selcom can reach it and that your server's outbound address meets Selcom's account allowlisting requirements. This package does not change your server's VPN or firewall configuration.

## 6. Initiate a payment

**This command initiates an actual customer payment prompt when live credentials are configured.** Replace the API key, customer details, and reference. Use an approved test customer/account during provider acceptance testing.

```sh
curl -sS --request POST 'http://127.0.0.1:3080/api/v1/payments/mobile' \
  --header 'Content-Type: application/json' \
  --header 'X-API-Key: REPLACE_WITH_APP_API_KEY_FROM_ENV' \
  --header 'Idempotency-Key: payment-ORDER-1001' \
  --data '{
    "merchantReference": "ORDER-1001",
    "phone": "255712345678",
    "amount": 1000,
    "currency": "TZS",
    "customerName": "Customer Name",
    "customerEmail": "customer@example.com",
    "description": "Order payment"
  }'
```

In Windows PowerShell, use `curl.exe` or `examples/pay.ps1`. The PowerShell example takes the application key from `.env` and prompts for customer details; it does not print that key.

An accepted request returns HTTP **202**, a `paymentId`, and a status such as `awaiting_authorization`. The customer must approve the prompt on their phone. **202 is not payment completion.** Amounts are whole TZS, not cents. Phone input accepts `07...`, `06...`, `255...`, and `+255...` mobile formats; name and email are required.

Keep both `merchantReference` and `Idempotency-Key` unchanged when retrying the same intended payment. A changed payload with the same key returns 409. Reusing a reference with another key also returns 409. An uncertain timeout must be investigated through status queries, not a new charge/reference.

### Retrieve the saved payment

```sh
curl -sS 'http://127.0.0.1:3080/api/v1/payments/PAYMENT_UUID' \
  --header 'X-API-Key: REPLACE_WITH_APP_API_KEY_FROM_ENV'
```

### Refresh from Selcom

```sh
curl -sS --request POST 'http://127.0.0.1:3080/api/v1/payments/PAYMENT_UUID/refresh' \
  --header 'X-API-Key: REPLACE_WITH_APP_API_KEY_FROM_ENV'
```

A refresh respects the next allowed query time and never resends a payment prompt. `nextCheckAt` shows when the next query is due. A signed callback can schedule an earlier status verification.

### List payments

```sh
curl -sS 'http://127.0.0.1:3080/api/v1/payments?page=1&pageSize=20&status=succeeded' \
  --header 'X-API-Key: REPLACE_WITH_APP_API_KEY_FROM_ENV'
```

All routes except health and the separately authenticated callback require `X-API-Key`. This is a server-to-server key; do not put it in public browser JavaScript. Amounts in responses are decimal strings to preserve precision.

## Payment states and storage

| Status | Meaning |
| --- | --- |
| `pending` | Recorded or creating the provider order |
| `awaiting_authorization` | Prompt accepted or provider still processing |
| `succeeded` | Authenticated order-status response confirms completion and matching amount/currency |
| `failed` | Explicit provider rejection |
| `cancelled` | Provider reports cancellation |
| `unresolved` | Timeout, malformed response, mismatch, or uncertain outcome; do not initiate another collection |

`manualReview=true` indicates automatic checks have reached their limit. Authenticated refresh remains available at the provider query interval. A later valid callback can reopen reconciliation of a previously failed/cancelled case. A confirmed success is never overwritten by a stale pending/error response.

- `payments`: payment identity, customer information, status, initiation stage, idempotency, and reconciliation claims.
- `payment_attempts`: each outbound operation, sanitized audit payloads, HTTP/transport outcomes, and timing.
- `webhook_events`: received callback payloads, signature verification outcome, and processing state.
- `schema_migrations`: migration bookkeeping.

The event and its scheduled status check are committed together. Callbacks are deduplicated independently of delivery timestamp, acknowledged quickly, and verified through the worker. Their unsigned amount/phone/channel fields cannot independently mark a payment paid. Full callback bodies contain payment/customer information; restrict database access and apply an appropriate retention policy. General logs and attempt logs redact credentials and customer details.

The worker only queries status. It never recreates orders or resends collections. A crash during dispatch leaves an uncertain stage to reconcile/review. If order creation was definitively saved but the prompt was never dispatched, replaying the same original request can claim that remaining step once.

SQL claims prevent simultaneous workers from checking the same payment. Claims expire after the HTTP deadline plus a buffer. Queries stop at the configured maximum attempts; unresolved rows stay available for review. All timestamps are stored in UTC and API dates include `Z`.

## Provider details to confirm in your account

The implementation follows the public Checkout API and uses HMAC-SHA256 callback verification with the signed identifier/status fields. Confirm your merchant's assigned collection URL, credentials, enabled channels, and callback signing configuration with Selcom. Twenty-character hexadecimal order/transaction IDs are used; public docs do not state their maximum lengths.

The public checkout docs do not define the acknowledgment body. This project returns HTTP 200 with `{"result":"SUCCESS","resultcode":"000","message":"Accepted"}` after storage. Confirm that acknowledgment with your provider contact. `WEBHOOK_MAX_SKEW_SECONDS` defaults to five minutes; if legitimate retries retain older signed timestamps, agree an appropriate window and keep system clocks synchronized. An invalid signature is rejected, not silently accepted.

Source references: [Selcom API documentation](https://developers.selcommobile.com/) and [official Node.js client](https://github.com/selcompaytechltd/selcom-apigw-client-nodejs). The package's `apigwCLient` export is checked; its unbounded HTTP helpers are not used.

## Tests and maintenance

```sh
npm ci --include=dev
npm test
```

The default tests are offline, use an in-memory repository and mocked Selcom, and require no real credentials. See `TESTING.md` for SQL integration commands. No automated test creates a real charge.

`npm run reconcile` performs one bounded batch for operational use. When using cron instead of the built-in worker, set `RECONCILE_ENABLED=false`, then schedule the command from this project directory. Leave the query interval at three minutes or longer.

Back up the database, keep `.env` private, and retain payment records across deployments: removing idempotency records removes their duplicate-request protection. Review unresolved payments before opening a new payment attempt. This project records collections; it does not perform refunds or merchant settlements.
